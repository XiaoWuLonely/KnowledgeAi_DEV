## 系统架构

当前为 Spring Boot 单体应用，所有业务模块部署在同一 JVM 进程内，通过包结构实现逻辑分层。该架构适合当前学习、演示和 MVP 交付目标。

### 本地开发链路

浏览器 → Vite Dev Server (:5173) → Spring Boot (:8080) → PostgreSQL (:5432)

### 部署架构（Docker）

Spring Boot (Java 21) 连接 PostgreSQL + pgvector (Docker)，外部依赖阿里云 OSS（头像存储）和 OpenAI 兼容 AI 模型 API。

## Java 源码包结构与模块职责

### 配置层 config/

SecurityConfig — 安全配置（JWT 无状态鉴权、接口权限）
JwtProperties — JWT 密钥与过期配置

AiProperties — AI 配置属性（base-url, api-key, model...）

## 数据流概览

### 核心流程

1. 认证 → JWT 登录 → 后续请求携带 Authorization: Bearer <token>
2. 聊天 → 用户发消息 → 组装上下文（历史 + RAG 文档）→ 调用 AI 模型 → 流式/非流式返回
3. 知识库 → 用户创建知识库 → 上传文档 → 后台异步处理（提取文本 → 分块 → 生成 Embedding）
4. RAG 检索 → 用户提问时 → 语义向量检索 + 全文关键词检索 → 加权融合 → 返回相关文档段落
5. 设置 → 用户可自定义 AI 模型供应商、API Key（加密存储）、RAG 参数、界面偏好

### 数据流图

前端 <--REST / SSE--> ChatController
  → ChatService / ChatStreamingService
  → ChatGenerationService
  → OpenAiCompatibleChatModelClient（调用 AI 模型 API）
  → ChatDocumentContextService（组装 RAG 上下文）
  → DocumentRetrievalService（向量 + 全文混合检索）
  → 各 Repository → PostgreSQL（Flyway 迁移管理）

## 安全设计

### 认证与鉴权

- JWT 无状态认证：登录后颁发 JWT access token
- 接口权限：/api/auth/** 和 /api/health 公开，其余需认证
- 资源级权限：知识库成员角色（OWNER / EDITOR / VIEWER）控制 CRUD 权限

### 敏感数据处理

| 数据类型          | 存储方式                                       | 返回方式                   |
| ------------- | ------------------------------------------ | ---------------------- |
| 用户密码          | Spring Security 密码编码器哈希                    | 永不返回                   |
| 用户 API Key    | AES-256 加密（密钥来自 KNOWFLOW_MODEL_SECRET_KEY） | 脱敏返回                   |
| JWT 密钥        | 环境变量 KNOWFLOW_JWT_SECRET                   | 永不返回                   |
| OSS AccessKey | 环境变量                                       | 永不返回                   |
| 头像            | DB 仅存 OSS object key                       | 后端代理返回图片内容             |
| 系统诊断          | 仅返回 DB 可达性、任务计数、模型配置布尔状态                   | 不暴露 Base URL、API Key 等 |

### 错误脱敏

- 全局异常处理器对 AI 模型供应商错误进行脱敏
- 不在响应 body、toast、日志中暴露 API Key 或 Authorization header

## 异步处理

文档处理采用异步编排模式：

1. 用户上传文档 → 同步创建 documents 行 + document_processing_jobs 行（QUEUED）
2. DocumentProcessingAsyncWorker（@Async）消费队列 → 状态机流转
3. 处理阶段：PARSING → CHUNKING → INDEXING → EMBEDDING
4. 进度实时更新 progress_percent 和 stage
5. 前端轮询获取进度

`knowflow.documents.processing.async-enabled` 默认 true（`application.yaml`），上传请求快速返回；测试或需要同步执行时设 false。embedding 按每批 64 个 chunk 分批调用，避免大文档单次请求超时。Chat 流式生成复用 Spring 管理的线程池（`TaskExecutor`），不再每个请求新建裸线程。

## 架构演进方向

当前单体架构适合 MVP 阶段。后续演进方向：

1. 模块拆分：将 document 和 chat 拆为独立微服务
2. 消息队列：引入 RabbitMQ / Kafka 解耦文档处理异步任务
3. 向量数据库：embedding 存储和检索迁移至专用向量数据库（Milvus、Qdrant）
4. 分布式会话：引入 Redis 管理 SSE 流式连接和会话状态
5. API 网关：使用 Spring Cloud Gateway 统一鉴权、限流、路由
6. 可观测性：集成 Micrometer + Prometheus + Grafana 监控体系
